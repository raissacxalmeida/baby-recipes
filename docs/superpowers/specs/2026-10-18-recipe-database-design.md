# Recipe database: design

Extends `2026-10-14-baby-recipes-design.md` and `2026-10-15-accounts-sync-design.md`. Same app, same accounts, same look. "My call" marks a decision the author did not make; everything else was decided by the author in conversation.

## Intent

Every recipe today is generated by OpenAI, even when an almost identical one was generated for another parent yesterday. That costs tokens and money, and the parent waits for the model. This adds a database of recipes (the "catalogue") that the app checks first. OpenAI is called only when the catalogue has nothing suitable left for that parent, and every recipe OpenAI writes is saved to the catalogue so nobody pays for it twice. The catalogue starts with 49 baby recipes from a cookbook, so it is useful from day one.

## Users

The same small, invited group as the rest of the app. Parents never see the catalogue as a list and never know where a recipe came from. They type the ingredients they have and get a recipe, as they do today.

## Behaviour

1. **Lookup first, OpenAI second.** When a parent asks for a recipe, the server first looks for a suitable catalogue recipe. If it finds one it returns it with no OpenAI call. If there is none it calls OpenAI as today. The request keeps the same validation as today, in the same order: ingredient list shape and limits, birthday set, baby at least 6 months old (the "too young" case).
2. **A catalogue recipe is suitable when all of these hold:**
   - **Age.** The baby's age in months is at least the recipe's `ageFromMonths`, and the recipe passes the existing `checkSafety` for the baby's age (that is what enforces the texture rule: puree only under 9 months and from 12; mashed from 6; soft-pieces from 9; finger-food from 12). The check is also run at serving time, even for seeded recipes.
   - **Ingredients.** It matches the parent's ingredients by the rule in "Matching" below.
   - **Not seen by this parent.** Its title is not among the titles this parent was already shown, disliked, or liked. Today's exclusion list is shown plus disliked; liked titles are added so a recipe that fell out of the 50 most recent shown titles cannot come back (my call).
3. **Which one, when several are suitable (my call).** The one that uses the most of the parent's ingredients first, then the one with the fewest ingredients the parent did not list, then a stable order (title). The parent's "another" button asks again, so it walks down this list; the one just disliked is excluded by rule 2.
4. **Serving a catalogue recipe.** It is returned in exactly the shape `POST /api/recipe` returns today (id made from the title as now, `ingredients` with `inList` flags, `allergens`, texture, portions), recorded in the parent's shown titles like any generated recipe, and costs nothing: **it does not use any of the parent's daily recipe or call allowance** (author's decision). A parent who has reached the daily limit still gets catalogue recipes; the "daily limit reached" message only appears when the catalogue has nothing left and OpenAI would be needed. Admins behave as today.
5. **When OpenAI is needed.** Today's rules apply unchanged: reserve the recipe and call allowance, up to 3 attempts, safety check, release the reservation on failure. The one change is the prompt: the list of titles to avoid is the parent's own seen titles **plus up to 30 catalogue titles that overlap with the parent's ingredients** (author's decision: OpenAI must be told which recipes we already have so it does not write them again). Which 30: those sharing the most ingredients with the parent's list, ties broken by title (my call). The existing check that rejects a generated recipe whose title is in the avoid list stays.
6. **Saving what OpenAI writes.** A recipe that passed validation and the safety check is saved to the catalogue before it is returned, unless one with the same normalised title is already there (then nothing is saved). Its `ageFromMonths` is the baby's age at that moment (my call: conservative; the texture check at serving time covers the rest). The catalogue stores no user id for it, so there is no way to tell who triggered it (my call, in the spirit of the community page). If saving fails, the parent still gets the recipe and the error is logged; saving must never turn a good response into an error.
7. **Seeding.** The 49 cookbook recipes in `docs/superpowers/specs/2026-10-18-recipe-database-seed/recipes-seed.json` are loaded into the catalogue automatically when the server starts, after migrations (my call: no manual step to remember, like migrations). Loading is idempotent: running it again adds only missing recipes, never duplicates, and never overwrites or removes a recipe saved from OpenAI. Seeded rows are identified by the file's `sourceId`. The seed file must be copied out of `docs/` into the server source (the Docker image excludes `docs/`), and must be inside the built container.
8. **Nothing user-linked.** Deleting an account or removing a person never changes the catalogue.
9. **Nothing else changes for the parent.** No new screen, button or label. The recipe screen, Liked, Community, sharing and portion scaling work as before; a catalogue recipe can be liked, disliked and shared like any other.

## Matching

A recipe matches when **every main ingredient of the recipe is among the parent's ingredients**. Ingredients that are not main may be missing: "it's ok they can get around using something else" (author). Extra ingredients the parent has but the recipe does not use are fine.

- **Comparing names** starts from the existing `isListed` / `normalizeIngredient` in `src/shared/ingredients.js`, so plurals and extra words work as they do for the `inList` flags today ("chicken" covers "chicken breast"). One known gap: `isListed` counts "potato" as listing "sweet potato", which is harmless for the highlight flags but wrong for choosing a recipe, because a parent with plain potatoes must not be served a sweet potato recipe. Matching must not let an ingredient stand in for a different food whose name ends with it. How is left to the builder (my suggestion: a short list of compound foods such as "sweet potato" that are only matched by their full name); the flags on the recipe screen may keep today's behaviour.
- **Main ingredients (my call, tuned on the seed file):** an ingredient is main if it is not a pantry ingredient and either (a) it is meat, fish or egg (reuse the keyword lists in `src/shared/recipeGroup.js`), however little there is, or (b) its grams are at least 10% of the total grams of the recipe's non-pantry ingredients. Pantry ingredients are never main: oils, butter, water, juices, stock and tea, tomato paste, spices and dried herbs, fresh herbs, garlic, lemon, carob and cocoa, yeast, cinnamon and vanilla. On the 49 seed recipes this gives 3 main ingredients on average (at most 6). The pantry list is one shared file with tests, like the group keywords.
- Main ingredients are worked out the same way for seeded and OpenAI recipes, from the stored grams.

**Pinned examples (tests):**

## Seed data

- **Source.** The author's file `~/Desktop/receitas.json`: an English translation of a German baby-food cookbook (49 recipes, plus 3 generic "porridge principle" templates that are not imported).
- **What was done to it** (already done, reviewable): every recipe was rewritten by hand into the app's recipe shape. Ingredients are in grams, steps contain no amounts, and the 20 family recipes were cut down to the baby's share. Salt, sugar, soy sauce, pepper and similar were removed; whole milk became "breast milk or formula"; low-salt stock became water; chopped nuts became ground. The 24 purées were rewritten as `mashed` with a last step to blend smooth or mash to the baby's stage, so they are suitable at every age from 6 to 11 months. All 49 pass `validateRecipe` and `checkSafety`. `seed-review.md` lists what changed in each recipe, and the quantities scaled for the baby are estimates.
- **File shape.** A JSON array; each item has `sourceId`, `id`, `title`, `ageFromMonths` (6 to 12), `basePortions` (1 to 12), `texture`, `ingredients` (`name`, `grams`), `steps` and `allergens`. The server must still run each seed recipe through `validateRecipe` and `checkSafety` when loading and refuse to load one that fails, so a later edit to the file cannot put an unsafe recipe in the catalogue.
- **How many a baby can get by age:** 18 at 6 months, 22 at 7, 25 at 8, 28 at 9, 40 at 10 and 11, 49 at 12 (before the ingredient match). The nine hand-held recipes (rolls, waffles, rösti and similar) are finger-food and only reach 12-month-olds.
- **Licensing (accepted risk, author's call).** The text derives from a commercial cookbook, rewritten in new wording. The author was told this and chose to go ahead. The app shows no source and no credit.

## Non-goals and anti-goals

- No catalogue screen, search, browsing, ratings, popularity ranking or "most liked" feeding back into which recipe is served.
- No admin tooling to edit or delete catalogue recipes in this version. A bad recipe is removed with SQL (my call). The mitigation is that every saved recipe has passed the safety check.
- The parent must never be told, or be able to tell, whether a recipe came from the catalogue or from OpenAI.
- Not a place to store who asked for what: nothing in the catalogue links to a user.
- Never serve a recipe that fails the safety or texture rules for the baby's age, even if the ingredients match perfectly.
- Do not change the daily limits (10 recipes, 30 OpenAI calls) or how they are counted for the OpenAI path.

## Constraints

- English UI and recipes, plain parent-friendly wording. No new UI is expected; if one turns out to be needed, follow the `add-screen` skill.
- Follow existing patterns: migrations are appended in `src/server/migrations.js` and new tables are added to `APP_TABLES` (test resets and backups read it); server logic next to `recipeService.js` / `generate.js`; tests in `test/`.
- Recipe validation and safety stay in `src/server/recipe.js` and `src/server/safety.js`; the catalogue code calls them, it does not copy them.
- The existing client contract for `POST /api/recipe` does not change.
- Tests are written first; the full suite, `npm run build` pass; the app container is rebuilt with the `deploy-docker` skill when done.

## Left to the builder

Table and column design (and any index), where the seed file lives in `src/`, how and where main ingredients are computed and stored, how "overlap" is scored for rules 3 and 5, how normalised titles are compared, the exact pantry keyword list beyond the groups above, how the start-up seeding is wired and logged, and the internal structure of the new server modules. Whether a parent who has used every catalogue match still sees the old behaviour (OpenAI) falls out of rule 5 and needs no extra code.
